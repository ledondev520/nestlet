# Manual service access and stable record references · schema10

Implementation candidate based on main6fba5cb. This is neither a pricing offer nor a claim of deployed billing, provider guarantees or security certification.

## Role versus service

Identity/roles and record ownership stay unchanged. The owner manages service configuration. Delegated administrators keep only their already-authorized diagnostic access; buying or enabling service never gives account administration, provider settings, another user's records or data-sharing consent.

Accounts without a service row retain the previous ordinary-user defaults: enabled, no expiry, ten AI requests per rolling hour. This default applies to existing and newly registered accounts; migration creates no paid status and no actual account grants. Owner AI behavior remains exempt from ordinary-user request limits. A manual configuration can enable/pause service, set an optional UTC expiry, and select one to thirty requests per rolling hour. All ordinary users still share thirty per rolling hour. Stored request counts survive restart; timestamps are UTC epoch milliseconds. Quota is reserved atomically before provider work and failed attempts still count. One primary application chat/extraction HTTP attempt is one allowance unit, including its bounded upstream retries/tool rounds (library chat can make up to four provider requests). This is not a count of individual upstream HTTP calls. Request receipts reconcile the same server-created request ID; different retries are different attempts. Model-generated titles, where integrated, use their own allowance reservation.

These are request limits, not token accounting or a money/spending cap. No price, card, payment processor, order, subscription, payment-success field, invoice or automatic renewal is added. Configuration is explicitly labeled manual and never claims a payment was received.

Paused/expired service blocks new AI work. It does not lock the user's own saved records, normal editing, original downloads or document exports. It does not revoke the user's independent saved-library disclosure permission; conversely library permission cannot bypass service availability. Existing request cancellation and authority gates remain. Access is checked before admission; this feature does not promise to recall content already sent or an already admitted provider request.

## HTTP and change review

- GET `/api/service`: authenticated own-account status/usage only.
- GET `/api/admin/services`: owner-only bounded account/service roster.
- GET `/api/admin/service-audit`: owner-only latest100 audit entries.
- PUT `/api/admin/accounts/:uuid/service`: owner-only, exact Origin/CSRF, HTTPS outside loopback, session rechecked after reading the bounded body. Exact body: enabled, expiresAt (canonical UTC ISO or null), requestsPerHour, expectedVersion. Unknown identity/role/price/payment fields are rejected.

A change and its minimal audit row are one SQLite transaction. Conflicting versions return409; exact lost-response replay reconciles without a second change or audit. The owner is immutable. The UI shows a review step and explicit confirmation; it does not configure a service merely by choosing a user. Ordinary users only see their own status, allowance and expiry. Input remains after uncertain saves and a fresh read is required before retry.

## Display references

Each saved entity has an additional `displayId`. Internal UUIDs, foreign keys, routes, source membership/version guards and external caseReference facts remain untouched. Prefixes are: KF customer, SX case/work item, CL material/original, WS document/artifact, DH conversation, XX message. Each uses eight decimal digits, e.g. `KF00000001`. Fact field keys such as property/rent are semantic fields and are not renumbered. Government case numbers are not changed or synthesized.

Numbers are unique within the authenticated account and entity kind. Migration backfills existing rows deterministically by creation time and UUID. Transactional insert triggers allocate subsequent numbers. Deleting a record preserves its reference as a tombstone; normal deletion/recreation, renaming and restart do not reuse numbers. Counter exhaustion aborts the new record atomically. Only currently exposed identifier surfaces change display; numbers are never authorization credentials or route inputs. Different accounts may have the same friendly reference, so the authenticated context remains essential.

A backup contains the known record map and counters. Restoring that recovery point preserves its references, but cannot know identifiers issued after the snapshot. Before an old-snapshot cutover the operator must assess later writes and high-water marks, or choose a newer recovery point. There is no claim of cross-disaster non-reuse when intervening history has been lost and no external numbering service is introduced.

## Migration and recovery

Schema9→10 is one additive transaction: service entitlements/audit/usage plus display-reference maps/counters/triggers. Existing tables, rows, credentials, identities, sessions, library choices and original bytes are preserved. A migration error rolls back the additions/version together. Prior schema9 binaries must not be started against schema10. The backup helper accepts schemas1–10; future11 is refused. A verified untouched schema9 snapshot remains the pre-upgrade recovery point.

Schema10 restore creates a new private copy, never overwrites the source or snapshot, and preserves record IDs/counters, owned data and usage receipts. It invalidates email actions, sessions and library grants under their existing schema guards. Additionally every ordinary account in the restored copy receives paused AI service, including accounts that previously used default service; a recovery audit distinguishes this from a manual UI change. Owner access remains available to review recovery. A fresh explicit owner decision is required before ordinary AI service resumes; reading/exporting existing records remains possible. Restore failure keeps INCOMPLETE and cannot be treated as a usable recovery.

Legacy schema1–9 restores stay at their historical schema and gain a private `nestlet.sqlite.service-reconfirm.json` fence in the restored directory only. Restore returns a content-free serviceRecovery state and preserveRestoreDirectory:true. Preserve the whole restored directory, including this sidecar and the matching database basename, for a schema10 cutover. Copying/renaming only the database discards the fence and is indistinguishable from an ordinary migration; that is not a supported protected cutover. The schema10 runtime serializes fence startup, validates its no-follow private file, identity, source-schema and standalone SQLite digest before opening SQLite for mutation, and refuses WAL/journal sidecars rather than auto-repairing them. Migration, ordinary-service pauses, audit and an immutable exact-fence receipt commit together. It consumes the fence only after commit. A leftover fence can be reconciled from the exact committed receipt without pausing a later explicit owner change again. A real process crash may also leave its startup lock: that lock blocks startup and requires the operator to verify that no process is using the recovered database and review the committed state before releasing it. Receipt reconciliation applies after that verified lock handling; it is not automatic crash recovery. An INCOMPLETE recovery directory, malformed/mismatched fences or stale startup locks fail closed for operator review; there is no recursive auto-repair or automatic stale-lock removal. Normal in-place migrations with no restore fence retain default compatibility. Old binaries do not understand this new fence; selecting an old-binary recovery requires explicit offline service-policy review before admitting traffic. This does not claim that old software automatically enforces new recovery rules.

Release is a separate decision: reviewed exact combined build/CI/browser evidence, verified database+original snapshot, isolated migration/restore rehearsal, disk capacity and prior-compatible recovery plan. No production migration, real service grant, billing operation or provider request is performed by this implementation task.
