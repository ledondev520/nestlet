# User → customer → case → conversations / artifacts: minimal contract v1

This is the coordinated implementation contract for the requested reusable case journey. Every record is scoped to the authenticated user_id. The administrator can manage service settings and existing operational metadata, but does not gain access to other users' customers, case bodies, conversations or artifacts. No workspace/team/invitation layer is added.

## Compatibility and migration

SQLite schema3 is one transactional additive migration from schema1/2. Existing users, case IDs, payloads, optimistic versions and operational events remain intact. Existing cases start with clientId:null; no customer identity is invented. Existing case endpoints remain compatible. New optional documentContext is stored inside the current payload_json; older-client updates that omit it or clientId preserve their existing values.

## Customers

- `POST /api/clients` `{displayName}` →201 `{client:{id,displayName,version,createdAt,updatedAt}}`
- `GET /api/clients?search=Johnny&limit=50` → `{clients:[...]}`; case-insensitive literal substring search of the user's own customer display names
- `GET /api/clients/:id` → `{client}`
- `PUT /api/clients/:id` `{displayName,expectedVersion}` → `{client}`
- `GET /api/clients/:id/cases` → `{cases:[metadata...]}`
- `GET /api/clients/:id/artifacts` → `{artifacts:[metadata...]}`

Display names are1–120 characters. They are friendly customer labels, not automatically verified legal names or document recipients. Duplicate display names may exist and remain distinguishable by IDs. Unknown/foreign IDs return404.

## Case association and confirmed document context

Existing create/update case payloads gain optional `clientId` (own customer UUID or null). General POST/PUT case CRUD rejects `documentContext` and `caseIssues` with 400 `CASE_INVALID`: write those only through the dedicated PATCH operations below. Omitting them on a legacy update preserves stored confirmations and issues. Returned case records include these fields. Existing version/expectedVersion concurrency remains unchanged.

`documentContext` is keyed by a fixed field set:
- documentDate
- recipientName, recipientOrganization, recipientContact, salutation
- senderName, senderRole, senderOrganization, senderContact
- attachments, nextActionOwner, targetDate

Each canonical record is `{value,source,confirmed,confirmedAt,notApplicable,sourceMessageId}`. Values/sources are bounded strings; sourceMessageId is null or a message belonging to a conversation in this user's case. Pending = not confirmed; resolved = explicitly confirmed or explicitly confirmed notApplicable. Confirmation time is server-generated by the dedicated confirm operation. Model suggestions never arrive confirmed.

- `GET /api/cases/:id/readiness?kind=followup&locale=zh` → readiness result `{ready,missing:[{key,question,reason}],...}`
- `PATCH /api/cases/:id/document-context` `{changes:{field:{value,source?,notApplicable?,sourceMessageId?}},factChanges?:{property?:{value,source?},...},confirm:boolean,expectedVersion,namesVerified?:boolean}` → `{case,readiness,regenerationRecommended:true}`

An unconfirmed proposal that differs from an already confirmed value returns 409 `DOCUMENT_CONTEXT_CONFLICT` without changing the case. `confirm:true` is the single explicit user “fill and continue” action, stamps confirmation time on the server, and can update existing core facts via factChanges in the same request. Omitted source is labeled “Direct user answer” for this action; the user need not type a source label. New model suggestions use confirm:false and remain unconfirmed. Unknown change properties are rejected before conflict handling. Already confirmed/resolved fields are included in future conversation context so the assistant does not ask for the same template facts repeatedly. This is persisted case knowledge, not autonomous or unlimited self-learning.

Incomplete working drafts remain saveable. Final operator documents require document-type-specific required facts and document fields to be supplied and reviewed. Unknown optional fields are omitted; required unknowns produce questions instead of invented values/placeholders. A final operator document is not an official completed government form or a compliance guarantee.


Case issues use `PATCH /api/cases/:id/issues` with `{changes:[{id?,question,status,resolution,sourceMessageId?}],expectedVersion}`. Status is pending, confirmed, or resolved; resolved requires a nonempty resolution. New IDs and updatedAt are server-generated. At most 30 issues are retained, question length is at most 500 characters, resolution at most 2000. This is an explicit user save, never automatic model resolution. Source message ownership is checked.

External letters require a reviewed property and confirmed recipient name or organization, recipient contact, sender name and sender contact. Status summaries require reviewed property and sender name. Date, salutation and attachments are optional: generation uses a neutral greeting or actual “Prepared on” date and omits unknown optional sections. No invented recipient, contact or case date.

## Conversations and messages

- `POST /api/cases/:caseId/conversations` `{title?}` →201 `{conversation:{id,caseId,title,createdAt,updatedAt}}`
- `GET /api/cases/:caseId/conversations` → `{conversations:[metadata...]}`
- `GET /api/conversations/:id` → `{conversation,messages:[...]}`

Message shape: `{id,conversationId,role,content,state,requestId,clientMessageId,createdAt}`. Roles are user/assistant; states are complete/interrupted/failed. Raw image base64 and uploaded binary files are never retained. A message may contain bounded image-presence metadata only, clearly marked not retained; reopening cannot pretend that those pixels are still available.

`POST /api/chat` gains optional conversationId and clientMessageId(UUID). With conversationId, send exactly one new user message in the existing messages array. The server resolves its own stored history and case; a supplied caseId must match. The new user message is saved once before starting the provider, and the assistant's completed or interrupted/failed text is retained with its truthful state. Reusing clientMessageId returns409 rather than silently paying for another response.

An SSE `conversation` event may identify `{conversationId,userMessageId}` before answer deltas. The final done/error identifies the persisted assistantMessageId when available. A completed result is not announced as durably saved if the database write failed. Disconnects preserve available partial text as interrupted; a process crash may leave the saved user turn unanswered, which is shown as incomplete on resume rather than fabricated as complete.

Legacy chat without conversationId remains compatible and transient. The new UI must create/select a conversation before calling chat when retention is desired. The provider context remains bounded; older history may be explicitly excerpted, while confirmed case facts/context are retained as authoritative working-copy context.

## Immutable English artifact versions

- `POST /api/cases/:id/artifacts` `{kind,title?,status:'draft'|'final',content,sourceConversationId?,sourceMessageId?,expectedCaseVersion}` →201 `{artifact}`
- `POST /api/cases/:id/artifacts/generate` `{kind,status:'draft'|'final',expectedCaseVersion}` →201 `{artifact}` using deterministic reviewed-document generation
- `GET /api/cases/:id/artifacts` → `{artifacts:[metadata...]}`
- `GET /api/artifacts/:id` → `{artifact}`
- `GET /api/artifacts/:id/download` → a plainly named English .txt attachment; existing print/PDF handling remains available in the UI

Kinds retain followup/missing-documents/status-summary. Each save appends an immutable version for that case/kind. Metadata includes id,caseId,kind,title,status,version,createdAt,sourceCaseVersion and optional conversation/message references. Full artifacts also include content and a bounded provenance snapshot generated from the case, not arbitrary client metadata.

Only complete, correctly scoped source messages may support a final artifact. Draft artifacts may retain incomplete work, visibly marked draft. Final creation runs document readiness and known-placeholder checks; no blanket claim that arbitrary content is legally compliant or government-approved.

## Authorization, bounds and outcomes

All mutation routes use the existing session, CSRF and exact-origin checks. IDs supplied by a client never replace the session's user ID. Validation rejects unknown keys and excessive text/record counts. Customer search/read responses and directory listings are bounded. Case deletion follows the existing explicit delete confirmation and also removes its conversations/artifacts; the frontend must say this clearly.

Limits and stable error codes will be supplied with the storage implementation before frontend freeze. Expected families: CLIENT_INVALID/CLIENT_NOT_FOUND/CLIENT_CONFLICT, CONVERSATION_INVALID/CONVERSATION_NOT_FOUND, MESSAGE_INVALID/CHAT_TURN_EXISTS/CHAT_SAVE_FAILED, DOCUMENT_NOT_READY, ARTIFACT_INVALID/ARTIFACT_NOT_FOUND/ARTIFACT_SOURCE_INCOMPLETE, CAPACITY_REACHED; existing authentication/case errors continue.

No production records or credentials are created during implementation tests. Actual SQLite migration, ownership isolation, restart recovery and concurrency are verified with disposable real databases; parser/stream fixtures must not be presented as paid-provider acceptance.
